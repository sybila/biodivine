# Context

This project is the "biodivine workspace". It is meant to be a collection of multiple repositories that depend on each other, but are technically not a single "monorepo" because they are intended to be individually accessible. Consequently, this project is itself a git repository, but each subfolder is also its own git repository, via submodules. The dependencies between repositories are not path-based, but either commit or version based. When working fully within one submodule, that's fine. However, when working across multiple submodules, you can temporarily change these dependencies to be path based and resolve dependencies that way. Upon final review, a human will push all changes (and/or release them) and update the version strings where necessary. You don't have to concern yourself with that, as long as the modified submodules all build properly when you are done.

The layout of the workspace (the library repositories, `biodivine-py` with the Python bindings of all libraries, and `biodivine-book` with the documentation of all libraries) is described in `README.md`. `biodivine-book` is a plain directory of this repository, not a submodule.

Note that each project most likely contains its own `AGENTS.md` file. When you start working in a specific project, always read that file before anything else. If you are updating a project-specific `AGENTS.md` file, don't copy instructions that are already covered by this file.

# Conventions

## Language, phrasing, etc.

 - Use American English unless instructed otherwise.
 - When writing documentation/reports/etc., always assume the reader of the text is not actually familiar with the instructions you have been given. Never explicitly mention/reproduce/reference user instructions in these texts. If it makes sense to explicitly state some instruction, you can have a "design goals/directions" section in the documentation or something similar; these should usually explain why the goal is reasonable and what are its tradeoffs.
 - For larger, high-level examples, there should always be a brief human-readable paragraph explaining what the example does (or what it demonstrates).
 - High level documentation (modules, readme, etc.) should always summarize and link to specific resources (other doc pages, specific types, etc.). Don't just list "critically important stuff"; be comprehensive, give signposts/lists of relevant resources, etc. based on which the user can orient themsleves and pick what they want to read next. For example, it's ok to briefly summarize what is placed where, even if the user has access to other navigation elements / menus / etc. 
 - Prefer placing examples / tutorials *before* technical deep dives or architecture discussion (to the reader, it is more important what the project does, and possibly why, not how).

## Rust development

 - Try to structure the code in such a way that each struct or non-trivial functionality has a separate internal module, but prefer to keep public APIs shallow via re-exports. For each code object (method, struct, etc.), pick one "canonical location" in the public API where it should be presented; don't re-export it in multiple locations. Either the set of code objects is so significant and self-contained that it does deserve a dedicated module, or it can be re-exported in the root module.
 - If you need a lot of extra internal code that is related to a particular feature (e.g. a struct), don't be afraid to introduce private sub-modules in the module where that struct is implemented (instead of creating a very long but self-contained file). For example, say that I have a `Reader` struct that internally implements several independent validation/aggregation steps and uses internal intermediate structures to pass this information between steps. A good structure would be (a) root module re-exports `Reader` from an internal reader-specific module (b) internal module defines reader and its logic (c) internal modules within the reader module define the reader-specific internal structures/algorithms that the reader then imports and uses. In well justified cases, these internal modules can directly add methods to `Reader` via additional `impl` blocks, but this should be rare.
 - Overall, the module structure should follow this recommendation: In the public API, everything should be in the root module, unless there is a well-defined and substantial subset of features that can be delegated to a separate public sub-module (obviously, this applies recursively, so a large sub-module can be again split based on features). A good self-test for whether a feature desrves a public submodule is whether the documentation for that submodule can present examples that demonstrate the functionality of that submodule in a meaningful way without relying too much on out-of-module features. Meanwhile, the internal modules should prioritize code readability. I should be able to determine where a major struct/method (including those that only appear in internal APIs) is located primarily by looking at the file tree of the project, not by tracing imports within modules.
 - Public API should be defensive but reasonable. Unless there is a good reason why a method should be public (especially methods used for testing/validation that the downstream users are unlikely to need), implementations should be private.
 - In documentation comments, when referencing structures/functions, strongly prefer using just the name, not the full quantified path. (e.g. [`Struct`] instead of [`crate::module::Struct`]; use [`StructX`](crate::module::StructX) if necessary).
 - Avoid unchecked integer conversions where possible (prefer explicit check with a panic, where this is truly required). Prefer having this as an explicit clippy rule.
 - Prefer types that ensure deterministic iteration order, if iteration is part of the desired functionality. Prefer having this as an explicit clippy rule. If iterating over unstable types, you can suppress the clippy warning, but always explain why this is valid.

## Other

 - Never work directly on main/master branch of the git repository. Prefer small, self-contained commits. Don't push anything; you should not have permissions to do that.
